# Интерактивное production-развёртывание

Запустите установщик из Ubuntu или WSL:

```bash
./deploy
```

Установщик подготавливает изолированное Python-окружение управляющего узла и,
после подтверждения, устанавливает недостающие Linux-пакеты. Редактировать
inventory или Vault вручную не требуется.

Установщик запрашивает:

- локальный либо удалённый ENTRY сервер и удалённый EXIT сервер;
- начальных SSH-пользователей и пароли;
- публичный административный ключ OpenSSH с компьютера оператора;
- текущие и новые SSH-порты;
- адреса и подсети; клиенты и публичный endpoint AWG3 по умолчанию используют
  UDP/443 соответственно на ENTRY и EXIT, а локальный AWG3-порт ENTRY
  выбирается отдельно без конфликта сокетов;
- прямую RU-маршрутизацию, SOAX или другой SOCKS5-прокси;
- серверы DoT и DoH;
- имя и профиль первого VPN-пользователя;
- при необходимости мониторинг через Telegram.

Для Telegram полная строка BotFather вида `1234567890:AA...` вводится как один
токен вместе с двоеточием. Отдельный chat ID должен быть числом; групповой ID
обычно имеет отрицательный вид `-100...`. Формат проверяется до создания
production inventory. Пустое поле Chat ID включает автоматическое определение:
после сообщения боту установщик получает последний доступный чат через Bot API.
Сохранённый числовой Chat ID можно повторно использовать на новых VPS.
Общий бот KalimeraWG отсутствует: оператор выбирает готового собственного бота
либо получает встроенную инструкцию `/newbot` для официального `@BotFather`.
Telegram-мониторинг можно не включать.
Если он включён, таймер запускается только после завершения настройки и
успешной строгой проверки обоих серверов.

SOAX предлагается как готовый вариант SOCKS5. Можно указать другой SOCKS5 с
необязательной аутентификацией. HTTP-only прокси не поддерживается. Поддержка
SOCKS5 UDP определяется автоматически реальным `UDP ASSOCIATE`: при отсутствии
UDP TCP-трафик и DoH используют прокси, а RU UDP получает прямой fail-open через
ENTRY.

Для первого и последующих клиентов команда `vpn-user` предлагает профили
`performance`, `balanced`, `masking`, `mobile` и `old`. Значения `Jc/Jmin/Jmax` выбираются
индивидуально в границах профиля. Параметры `S`, диапазоны `H` и подписи `I`
современного клиента точно совпадают с интерфейсом ENTRY, к которому он
подключается. Профиль `mobile` использует отдельный интерфейс, прямой UDP/8443 и
QUIC Initial-подобный `I1`, проверенный в официальном iOS-клиенте. Профиль `old`
использует отдельный интерфейс с одиночными `H`.

Адрес клиента формируется с префиксом выбранной VPN-подсети: при стандартных
значениях это `10.66.0.2/24`, а не `10.66.0.2/32`. Такой адрес создаёт на
Keenetic связанный маршрут к `10.66.0.0/24`, поэтому внутренний DNS
`10.66.0.1` доступен через AWG без ручного статического маршрута. Клиентский
`AllowedIPs` содержит только `0.0.0.0/0, ::/0`; отдельный DNS-префикс больше не
нужен. Серверный `AllowedIPs` пира по-прежнему обязательно содержит только
адрес самого клиента `/32` для cryptokey routing и проверки источника.

Новые установки сразу используют пакет с формой QUIC v1 Initial и итоговым
размером 1200 байт. На прежней установке режим применяется явно без ротации
ключей, пиров и параметров `J/S/H`:

```bash
./deploy --resume --mobile-i1-mode quic-ios
vpn-user iphone mobile
```

Повторный `--resume` сохраняет уже созданный `I1` и не меняет его случайно.
Ранее выданный mobile-конфиг с другим `I1` после переключения не подходит.
Для совместимости возможен возврат к DNS-подобному варианту:

```bash
./deploy --resume --mobile-i1-mode dns-ios
vpn-user iphone-dns mobile
```

Production inventory, созданный до появления отдельного mobile-интерфейса,
обновляется явной идемпотентной командой:

```bash
./deploy --resume --enable-mobile
```

Команда создаёт недостающий закрытый ключ внутри Ansible Vault, пустой список
mobile-пиров, непересекающуюся подсеть и профиль UDP/8443. Интерфейс остаётся
выключенным до создания первого mobile-клиента.

Вводимые пароли и tokens не отображаются. Начальные SSH-пароли используются
только для bootstrap. Установщик создаёт на ENTRY и EXIT пользователя
`kalimera`, а также новые независимые пароли `kalimera` и `root` длиной 30
символов. Четыре значения показываются ровно один раз для сохранения в менеджере
паролей. После этого необратимые SHA-512 crypt-хеши остаются для системных
учётных записей, а пароли `kalimera` хранятся только внутри зашифрованного Vault,
поскольку нужны Ansible для неинтерактивного `sudo`; штатной команды их
повторного показа нет.
Если образ VPS требует входа как `ubuntu` или другой sudo-пользователь,
установщик использует его только на первом этапе. После проверки нового канала
bootstrap-пароль и ссылка на него удаляются из inventory и Vault. Их заменяет
ссылка на отдельный пароль `kalimera`, который остаётся только в зашифрованном
Vault для автоматического `sudo`; дальнейшая автоматизация и оператор входят
исключительно как `kalimera`, а SSH-доступ root полностью отключается.
Установщику передаётся только однострочный публичный ключ OpenSSH; закрытый SSH-ключ
вставлять запрещено. Public key добавляется на оба сервера до отключения входа
по паролю.

Установщик автоматически:

1. до изменения состояния серверов проверяет системный DNS, ожидает его
   восстановления ограниченное время и включает повторные попытки APT;
2. создаёт и устанавливает отдельный SSH key управляющего узла;
3. создаёт AWG keys, PSK, зашифрованный Vault и первого peer;
4. определяет WAN-интерфейсы по основному IPv4-маршруту каждого сервера;
5. разрешает межсерверный AWG в UFW только между единственными постоянными
   публичными IPv4 ENTRY и EXIT;
6. выполняет аудит только для чтения;
7. создаёт `kalimera`, устанавливает его key-only доступ и ограниченный набор
   эксплуатационных команд без запроса sudo-пароля;
8. временно оставляет одновременно старый и новый SSH-порты;
9. проверяет вход `kalimera` по ключу через новые порты и ожидает подтверждения
   двух независимых сеансов;
10. переподключается через новые порты и удаляет старые прослушиватели и правила UFW;
11. включает Fail2Ban только после подтверждения окончательного SSH-доступа;
12. выполняет строгие проверки состояния ENTRY и EXIT, включая отсутствие
    общего межсерверного UDP-разрешения для всех адресов;
13. сохраняет готовую клиентскую конфигурацию за пределами репозитория;
14. показывает итог без секретов: SSH endpoints, схему каскада, DNS,
    защищённые пути клиентских файлов и краткую справку по командам.

APT-источники провайдера с `trusted=yes` не отключаются автоматически:
установщик показывает предупреждение с именем файла, чтобы оператор мог
проверить происхождение зеркала без неожиданного изменения сетевой политики VPS.

Для IP-фильтрации каждый публичный адрес AWG должен быть постоянным IPv4 либо
DNS-именем, которое во время установки разрешается ровно в один постоянный
публичный IPv4. Изменение адреса требует повторного запуска установщика.

Файлы с секретами находятся вне Git либо явно исключены:

- `inventory/production/`;
- `~/.config/awg-iac/production-vault.pass`;
- `~/.ssh/awg-iac-production`;
- `~/.local/share/awg-iac/production/clients/NAME.conf`.

При локальном запуске на ENTRY управляющие SSH-ключи, пароль Vault и production
inventory остаются на ENTRY. Это выбранная модель эксплуатации; для более
строгого разделения запускайте тот же установщик с доверенного отдельного
компьютера.

Кроме специально обозначенной одноразовой панели четырёх новых локальных
паролей, установщик никогда не печатает закрытые ключи, PSK, введённые пароли,
токены или содержимое клиентских конфигураций. Клиентский файл имеет права
`0600`; передавайте его только по доверенному каналу.

## Доменные политики

Политики хранятся как файлы «один домен на строку» в
`inventory/production/domains/`:

- `ru-domain` - RU-прокси либо прямой выход через ENTRY;
- `se-domain` - выход через EXIT;
- `entry-domain` - прямой выход через ENTRY.

Допускаются комментарии и пустые строки. После чистой установки все списки
пусты: установщик не классифицирует чужие домены вместо владельца системы.

## DNS

По умолчанию используются Mullvad DoT и Yandex DoH. В диалоге можно указать
проверенные IPv4 endpoints, TLS names и путь DoH без редактирования YAML.

После установки `dns-status` показывает фактические listeners, upstream,
источник настроек и результаты живых DNS-проверок. `dot-switch` меняет основной
DoT, а `doh-switch` - RU DoH через прокси. Обе команды сохраняют защищённое
локальное переопределение, учитываемое последующим deploy, и автоматически
возвращают предыдущую конфигурацию при ошибке проверки или перезапуска.

Локальных пользователей можно просмотреть, экспортировать и удалить командами
`vpn-user list`, `vpn-user export ИМЯ` и `vpn-user delete ИМЯ`. После создания
локального пользователя его полный конфиг также выводится в текущий терминал.
Для пользователя из Vault команда объяснит, что его закрытый ключ хранится
только на управляющем компьютере, а удалять такого пользователя нужно из
inventory, чтобы последующий deploy не вернул peer обратно.

## Режимы RU-маршрутизации

- **Напрямую через ENTRY:** прокси-службы выключены, RU ipsets сохраняют mark 0
  и используют обычный WAN-маршрут ENTRY.
- **SOAX:** SOCKS5 SOAX переносит RU TUN-трафик и Yandex DoH.
- **Другой SOCKS5:** та же схема маршрутизации и DNS использует заданный SOCKS5.

Команда `ru-proxy-set` создаёт постоянное локальное переопределение endpoint и
учётных данных, проверяет конфигурацию, восстанавливает `sb-ru` и таблицу `200`,
а затем повторно определяет поддержку UDP. Переопределение хранится на ENTRY с
правами `0600`, не выводится и не помещается в Git.

## Повторное применение

Обновить только оформление терминала и справку на ENTRY и EXIT, не затрагивая
SSH, AWG, UFW, DNS, MTU и маршрутизацию:

```bash
./deploy --terminal-only
```

Этот режим не выполняет SSH-переход, не перезапускает VPN-интерфейсы и не
запускает полное повторное развёртывание.

Применить уже созданное развёртывание без начальных паролей:

```bash
./deploy --resume
```

Транзакционно обновить AmneziaWG и применить проверенные версии sing-box/AWG3
из текущего выпуска репозитория:

```bash
./deploy --resume --update-components
```

Перед изменением оба сервера сохраняют предыдущие пакеты локально. После
установки выполняется полная проверка каскада; при ошибке inventory и пакеты
ENTRY/EXIT автоматически возвращаются к прежнему состоянию. Фоновое обновление
критических компонентов не выполняется.

Показать сохранённый итог без подключения к серверам и без изменений:

```bash
./deploy --summary
```

Удалённые имена ENTRY, EXIT и AWG endpoints должны разрешаться в публичные IPv4.
В локальном режиме только транспорт Ansible использует `127.0.0.1`; публичный
IPv4 ENTRY автоматически определяется по исходному адресу реального маршрута до
EXIT. Если VPS находится за NAT и публичного адреса на интерфейсе нет,
установщик не угадывает его и просит указать опубликованный endpoint явно.
Имена WAN-интерфейсов определяются по основному IPv4-маршруту, поэтому установка
не зависит от соглашений конкретного хостинга. Требуется Ubuntu 24.04 LTS;
поддерживается 24.04.4 и последующие обновления безопасности и точечные
обновления ветки 24.04.
