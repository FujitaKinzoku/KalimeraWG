# Резервный EXIT

Второй зарубежный сервер, на который ENTRY сам переводит зарубежный трафик, когда
основной EXIT перестаёт отвечать. Клиентские конфиги, ключи и точка входа не
меняются: клиенты подключаются к ENTRY как раньше.

## Что это даёт

| Отказ | Без резервного EXIT | С резервным EXIT |
|---|---|---|
| Основной EXIT или его хостер недоступен | зарубежный трафик стоит до замены сервера | переключение примерно за 30-40 секунд |
| Адрес или сеть основного EXIT закрыты из России | то же | переключение, если резервный в другой сети |
| Перезагрузка EXIT (`cascade-reboot`) | перерыв на время загрузки | серверы перезагружаются по одному; перерыв до 40 секунд |
| Не отвечают оба сервера | - | трафик отклоняется, с адреса ENTRY он не выходит |

Резервный EXIT не защищает от отказа ENTRY и от блокировки самого протокола на
обоих путях сразу.

## Как выбрать сервер

- Другой хостер, другая автономная система и по возможности другая страна, чем у
  основного EXIT: общая сеть закрывается целиком.
- Чистая Ubuntu 24.04, публичный IPv4, вход по SSH с паролем: по нему установщик
  один раз ставит управляющий ключ.
- До покупки проверьте с ENTRY, что сеть хостера открывается. Команда выполняется
  от обычного пользователя и идёт напрямую с ENTRY, мимо туннеля:

  ```bash
  curl -s -o /dev/null -m 30 -w 'connect=%{time_connect} size=%{size_download}\n' https://АДРЕС-ТЕСТОВОГО-ФАЙЛА-ХОСТЕРА
  ```

  `connect=0.000000` - соединение не открылось, сеть закрыта. Для сравнения та же
  команда с `--interface awg3` идёт через основной EXIT.
- Открытая сеть ещё не значит хороший маршрут: он может терять пакеты, и тогда
  скорость через туннель упадёт в десятки раз. Проверьте это с нового сервера,
  пока он не подключён (в каскаде с FRONT; порт 443 FRONT открыт для всех):

  ```bash
  for i in $(seq 1 30); do curl -4 -s -o /dev/null --max-time 10 -w '%{time_connect} %{time_total}\n' https://ORIGIN-ДОМЕН-FRONT/; done
  ```

  Все строки должны быть близки друг к другу. Строки, где время больше на
  полсекунды-секунду, - потерянные пакеты; если таких заметная часть, сервер
  в резерв не годится. Ту же проверку установщик делает сам перед подключением.

## Подключение

На ENTRY:

```bash
kalimera-deploy --resume --enable-standby-exit
```

Установщик спросит адрес сервера, пользователя, текущий и новый SSH-порт и пароль,
установит на сервер управляющий ключ, создаст ключи второго туннеля и выполнит
обычный deploy. Основной EXIT и клиентские конфиги не затрагиваются. В конце
установщик попросит подтвердить вход на новый сервер по ключу: это тот же
двухшаговый переход SSH, что и при первой установке.

До того как что-либо изменить, установщик проверяет маршрут от ENTRY до нового
сервера: сто TCP-подключений к его SSH-порту, около 20 секунд. Подключение,
занявшее секунду и больше, прошло со второй попытки - пакет потерялся. Если
таких 2% и больше, установщик показывает счёт и спрашивает, подключать ли сервер;
при отказе inventory и сервер остаются как были.

Учётные записи на резервном EXIT те же, что на основном: `kalimera` с тем же
паролем sudo. Вход по SSH на обоих только по ключу. Отдельный пароль для нового
сервера не создаётся и на экран не выводится: действует пароль «EXIT · kalimera»,
показанный при установке каскада.

Работает только с kernel-модулем AmneziaWG (он используется по умолчанию).

## Отключение и замена

На ENTRY:

```bash
kalimera-deploy --resume --disable-standby-exit
```

Установщик убирает сервер из inventory и его ключи из Vault, затем обычный deploy
снимает на ENTRY второй туннель и переключатель путей. Каскад возвращается к
одному зарубежному серверу, клиентские конфиги не меняются. Команда отказывает,
пока зарубежный трафик идёт через резервный EXIT: сначала верните его на
основной (`exit-path status`, `exit-path use primary`).

Сам отключённый сервер не изменяется - он может быть уже недоступен. На нём
остаются ключи его туннеля, его доля ключа хранилища и зашифрованная копия
состояния контроллера. Остальные серверы после deploy долей ему не выдают, одной
его доли для открытия хранилища мало. Удалите сервер у хостера или переустановите
на нём систему.

Замена сервера - это отключение и новое подключение: сначала
`--disable-standby-exit`, затем `--enable-standby-exit` с адресом нового сервера.

## Как это устроено

- На ENTRY два туннеля: `awg3` до основного EXIT и `awg4` до резервного. У каждого
  свои ключи, служебная подсеть и профиль маскировки.
- Маршрут таблицы EXIT ведёт в один из них. Какой именно, решает переключатель
  путей: служба `kalimera-exit-path` запускается каждые 10 секунд.
- Проверка туннеля - TCP-соединения через него к трём независимым адресам. Туннель
  считается живым, пока отвечают два из трёх. Свежего handshake для этого мало: он
  есть и тогда, когда EXIT потерял выход в интернет.
- На резервный путь трафик уходит после трёх неудачных проверок основного подряд
  и только если резервный отвечает.
- Обратно на основной - когда он непрерывно отвечает 15 минут. Иначе внешний адрес
  клиентов менялся бы при каждом коротком сбое связи.
- Если не отвечают оба, маршрут не меняется.
- При переключении ENTRY забывает соединения прежнего туннеля (conntrack),
  закрывает собственные сокеты на его адресе (соединения клиентов VLESS) и, если
  зарубежный DNS идёт через EXIT, переводит Unbound на резолвер действующего EXIT.
- О каждом переключении приходит сообщение в Telegram, если мониторинг включён.
- Во время deploy переключатель проверяет туннели, но путь не меняет.

Что видит клиент при переключении: открытые соединения обрываются и сразу
открываются заново, внешний адрес меняется, часть сайтов попросит войти снова.

## Команды

Все команды выполняются на ENTRY.

| Команда | Что делает |
|---|---|
| `exit-path` или `exit-path status` | через какой сервер идёт трафик, состояние обоих туннелей, последнее переключение |
| `exit-path drill` | учебное переключение на резервный EXIT на 5 минут; `--minutes N` задаёт длительность |
| `exit-path use standby` | закрепить резервный путь, например на время работ с основным EXIT |
| `exit-path use primary` | закрепить основной путь |
| `exit-path auto` | вернуть автоматический выбор, прервать учение |

Закрепление командой `use` переживает перезагрузку ENTRY. Закреплённый путь не
меняется, даже если сервер перестал отвечать.

## Качество пути

Путь может отвечать и при этом терять пакеты: соединения открываются, а скорость
в десятки раз ниже обычной. Поэтому под строкой каждого пути `exit-path status`
показывает задержку и счёт потерь за последний час:

```text
резервный EXIT (awg4): отвечает (3 из 3), без сбоев 44 мин
  задержка 96 мс; за час 61 из 1080 проверок прошли со второй попытки или без ответа (5,6%): путь теряет пакеты
```

Проверка «со второй попытки» - подключение, занявшее секунду и больше: первый
пакет соединения или ответ на него потерялся, и ядро отправило его повторно.
Доля таких проверок примерно вдвое больше доли потерянных пакетов. При 2% и
выше путь считается теряющим пакеты, и `cascade-check` показывает замечание.

На выбор пути потери не влияют: переключение происходит только когда путь
перестал отвечать. Проверить новый сервер до того, как на него придётся
положиться, можно так (на ENTRY, скорость через каждый туннель):

```bash
for dev in awg3 awg4; do curl -4 -s -o /dev/null --max-time 90 --interface "$dev" -w "$dev: %{size_download} байт за %{time_total} с\n" 'https://speed.cloudflare.com/__down?bytes=10000000'; done
```

## Проверка

`cascade-check` показывает:

- раздел «EXIT резервный: удалённый отчёт» и его строку в группе «СЕРВЕРЫ»;
- строки «пути до EXIT»: отвечает ли каждый туннель, не теряет ли пакеты и через
  какой идёт трафик;
- связь «ENTRY → EXIT резервный: SSH» и задержку через второй туннель.

Замечание (WARN) означает, что каскад работает без запаса: трафик идёт через
резервный EXIT, резервный не отвечает или теряет пакеты либо путь закреплён
вручную.

Пока трафик идёт через резервный EXIT, `awg-health --strict` на ENTRY сообщает
ошибку handshake основного туннеля. Служба самовосстановления в этом случае
основной туннель не перезапускает: причина вне ENTRY.

## Настройки

В `inventory/production/group_vars/entry.yml`, затем `kalimera-deploy --resume`:

```yaml
entry_exit_path_interval: 10s               # как часто проверяются туннели
entry_exit_path_fail_threshold: 3           # неудачных проверок подряд до переключения
entry_exit_path_failback_seconds: 900       # сколько основной должен отвечать до возврата
entry_exit_path_probe_quorum: 2             # сколько адресов из списка должны ответить
entry_exit_path_probe_targets:              # адрес и TCP-порт
  - [1.1.1.1, 443]
  - [8.8.8.8, 443]
  - [9.9.9.9, 443]
entry_exit_path_loss_warn_percent: 2        # доля потерь за час, с которой путь называется теряющим пакеты
```

## Ограничения

- Переключатель уходит с пути, который перестал отвечать. Путь, который отвечает,
  но теряет пакеты, он показывает в `exit-path status` и `cascade-check`, но трафик
  с него сам не уводит.

- MTU каскада один на оба пути: берётся наименьший из измеренных до обоих серверов.
- Перед перезагрузкой основного EXIT трафик заранее не переводится: переключатель
  срабатывает сам, перерыв - до 40 секунд. Чтобы обойтись без него, выполните
  `exit-path use standby` до перезагрузки и `exit-path auto` после.
- Сервер подключается один. Замена основного EXIT резервным отдельной командой
  пока не предусмотрена.
