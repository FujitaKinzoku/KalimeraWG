# Приёмочные испытания на чистых VPS

Полный цикл приёмки был успешно выполнен 6 августа 2026 года на двух
одноразовых VPS с Ubuntu 24.04: одном ENTRY сервере и одном EXIT сервере.

Первоначальный результат относился к AWG 2-конфигурации до выделения
межсерверного userspace-канала AWG 3+. Для KalimeraWG дополнительно применяется
отдельный цикл приёмки из `docs/awg3.md`: проверяются userspace-канал,
двусторонний PMTU, согласованный клиентский MTU и реальные современные клиенты.

Проверены следующие этапы:

- первоначальное развёртывание ENTRY и EXIT серверов;
- строгие проверки состояния без вывода секретов;
- повторное развёртывание с результатом `changed=0`;
- перезагрузка обоих серверов и автоматическое восстановление всех служб;
- прямая маршрутизация RU-трафика при выключенном прокси и возврат в прокси-режим;
- переход RU-прокси в fail-open и последующее восстановление;
- резервное копирование и откат ENTRY и EXIT серверов;
- финальные строгие проверки состояния с `changed=0`;
- пустые локальные политики доменов и прямых RU-портов после чистой установки;
- сохранение ручного прямого RU-режима после повторных развёртываний;
- актуальные рукопожатия AmneziaWG в обоих направлениях ENTRY↔EXIT;
- создание защищённой клиентской конфигурации вне Git;
- восстановление локальных peer-записей после повторного deploy и перезагрузки ENTRY;
- реальный импорт клиентской конфигурации, передача трафика и свежий handshake;
- активные таймеры аудита и обслуживания без неисправных systemd-служб.

Успешный итог управляющего узла:

```text
Приёмочные проверки чистых VPS пройдены: развёртывание, идемпотентность,
перезагрузка, переключение при отказе, восстановление и откат.
```

Реальные inventory, учётные данные, закрытые ключи, PSK, клиентские конфигурации,
журналы, runtime-состояние и содержимое резервных копий не сохраняются в
репозитории как тестовые артефакты.

Реальная клиентская конфигурация для проверки соединения оставалась защищённой
за пределами репозитория и никогда не включалась в вывод тестов.

## Дополнительная приёмка FRONT/CDN

Тестовая ветка FRONT требует третью чистую VPS и следующие проверки:

1. `kalimera-test` проходит на ENTRY, EXIT и FRONT.
2. `vless-user create test-cdn cdn` выводит JSON, который импортируется без
   ручного изменения XHTTP-параметров.
3. Новая сессия устанавливается через CDN при действующей внешней политике
   белых списков.
4. `vless-user create test-direct direct` создаёт отдельный JSON прямого
   TLS-пути через FRONT, без пользовательского inbound на ENTRY.
5. `ru-proxy off` не останавливает `kalimera-front-backend.service` и не
   разрывает основной маршрут через EXIT.
6. После перезагрузки FRONT реестр пользователей совпадает с активной
   конфигурацией Xray, а секреты открыты из 2-of-N хранилища.
7. `--replace-front` оставляет старый FRONT разрешённым до отдельного commit.
8. После переключения CDN origin и проверки новой сессии
   `--commit-front-replacement` удаляет временное UFW-правило старого FRONT.
9. До commit команда `--rollback-front-replacement` возвращает прежний
   inventory и рабочий endpoint.
10. После prepare повторный `vless-user export ИМЯ` для direct-пользователя
    содержит новый origin-домен, а CDN JSON сохраняет прежний CDN-домен.
11. После commit установщик явно требует выключить или переустановить старый
    FRONT и показывает его прежний адрес без секретных данных.

Параметры `packet-up`, GET uplink, XHTTP path, Nginx buffering/timeout,
публичный CDN-домен, пользовательские UUID и служебный REALITY backend не
должны меняться во время замены FRONT.
