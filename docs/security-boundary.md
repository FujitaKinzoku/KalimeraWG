# Граница безопасности

## Универсальная базовая защита

KalimeraWG применяет один профиль защиты на всех поддерживаемых VPS. Он не
меняет схему маршрутизации и не вводит отдельные режимы производительности или
`strict`. Меры, зависящие от особенностей ядра и образа хостинга, сначала
диагностируются и не включаются автоматически, если могут остановить AWG, TUN,
DNS, обновления или аварийное администрирование.

Обязательная базовая защита включает key-only SSH без banner и forwarding,
Fail2Ban, запрещающие политики UFW, изоляцию клиентских зон, отдельный
`Signed-By` keyring AmneziaWG, системный журнал только в RAM, безопасные
sysctl/systemd-настройки и контроль целостности статических управляемых файлов.
Содержимое пользовательского трафика, DNS-запросы и история команд не
записываются на диск.

Человеческий SSH-доступ после установки принадлежит отдельному пользователю
`kalimera`. Обычные команды проекта проходят через root-owned allowlist и не
требуют писать `sudo`; произвольный полный sudo требует пароль. Root SSH
полностью отключён на ENTRY и EXIT. Повторяемый Ansible-deploy также входит как
`kalimera` отдельным key-only ключом, ограниченным исходным публичным IPv4 и
запретом forwarding/PTY, а повышение прав выполняет через пароль `sudo`,
доступный только из зашифрованного Ansible Vault.

## Политика no-logs

| Категория | Политика хранения |
|---|---|
| содержимое и назначения трафика | обрабатываются для маршрутизации, но не записываются |
| DNS-запросы и ответы | query/reply logging отключён; dnsmasq, resolved и sing-box не кэшируют ответы |
| UFW и sing-box | журналирование соединений отключено |
| systemd journal | только `/run`, не более 32 MiB и двух часов |
| SSH-события для Fail2Ban | только в RAM внутри короткого окна journal |
| база и журнал Fail2Ban | только RAM; постоянная SQLite и отдельный log отключены |
| `wtmp`, `btmp`, `lastlog`, `faillog` | временные файлы в `/run`, исчезают после перезагрузки |
| история команд и coredump | постоянное хранение отключено |
| AWG endpoint, handshake, счётчики и conntrack | только оперативное состояние ядра/процесса в RAM |
| DNS-кэш Unbound | только RAM; на диск не выгружается |
| конфигурация пиров | сохраняется root-only: public key, PSK и внутренний VPN-адрес необходимы для подключения |
| обновления | сохраняются технические APT/dpkg-записи без истории пользовательского трафика |

Полное отсутствие состояния невозможно без остановки каскада: сервер обязан
знать разрешённые peer и держать текущие сетевые таблицы в памяти. Эта политика
запрещает именно постоянную историю действий и соединений, но сохраняет
минимальные данные, без которых повторное подключение клиента, DNS, защита SSH
и обновления не работают. Журналы хостинга, прокси-провайдера, DNS-upstream и
целевых сайтов находятся вне контроля KalimeraWG.

## Запрещено помещать в репозиторий или диагностические материалы

- Закрытые ключи AWG/WireGuard и предварительно согласованные ключи (PSK).
- Учётные данные SOAX, токены Telegram, закрытые SSH-ключи, пароли и пароль Vault.
- Полные клиентские конфигурации и QR-коды внутри репозитория или CI-артефактов.
- Выгрузки `journal`, сетевые дампы `pcap`, дампы памяти, состояние времени
  выполнения и реальные счётчики.
- Содержимое backup и архивы rollback.
- Необезличенный inventory с адресами, MAC, именами peers и частной политикой маршрутизации.

## Работа с секретами

Используется Ansible Vault. Реальный файл создаётся только внутри игнорируемого
Git каталога `inventory/production`:

```bash
ansible-vault create inventory/production/group_vars/all/vault.yml
```

Пароль Vault вводится интерактивно либо читается из файла за пределами
репозитория. Файл с паролем Vault нельзя размещать в дереве проекта.

Задачи, формирующие значения из секретов, обязаны использовать `no_log: true`.
Сформированные файлы с секретами получают права `0600`. CI использует только
пример inventory.

Интерактивный установщик создаёт начальную клиентскую конфигурацию только в
`~/.local/share/awg-iac/production/clients/`, вне Git, с правами `0600`. В выводе
показывается только путь, но не содержимое.

Команда `vpn-user` создаёт последующих клиентов непосредственно на ENTRY. Их
конфигурации находятся в `/root/awg-client-configs`, а минимальные peer-файлы -
в `/etc/awg`; оба каталога доступны только root и исключены из Git. Это
операционные секреты, которые нельзя включать в журналы или отчёты. Явная
команда `vpn-user export ИМЯ` и успешное создание пользователя выводят конфиг
только в вызывающий терминал, не создавая дополнительной копии и не записывая
его в серверный журнал. Оператор отвечает за защищённость буфера обмена и
должен отключить запись SSH-сеанса на своей стороне.

При выборе локального режима сам ENTRY одновременно становится управляющим
узлом: на нём остаются управляющий SSH private key, пароль Vault и production
inventory. Проект сохраняет этот явно выбранный режим. Для разделения доверия
установщик следует запускать удалённо с отдельного доверенного компьютера.

## Граница резервных копий

Все управляемые backup-пути должны находиться внутри `/root/config-backups`.
Перед копированием, перемещением, очисткой или rollback роль проверяет итоговый
путь. Резервные копии никогда не загружаются в этот репозиторий.

## Граница inventory

Пример inventory использует документальные адреса RFC 5737. Реальные публичные
адреса, метки пиров, публичные ключи, внутренние сети и доменные политики находятся
только в закрытом production inventory. Публичные ключи пиров не являются
криптографическими секретами, но рассматриваются как чувствительные метаданные.

Интерактивная команда `ru-proxy-set` хранит необходимую sing-box рабочую копию
учётных данных только на ENTRY в `/etc/awg/ru-proxy-override.json` с владельцем
root и правами `0600`. Это runtime-секрет вне Git; его содержимое не выводится,
а резервные копии остаются исключительно в `/root/config-backups`.

## Сетевой периметр UFW

На WAN-интерфейсе разрешены только управляемые SSH-порты и активные UDP-порты
AWG. DNS-порт 53 открыт только внутри клиентских AWG-интерфейсов. Входящая и
транзитная политики по умолчанию запрещающие. Исходящие соединения разрешены,
поскольку они нужны DNS-over-TLS/HTTPS, обновлениям, прокси и самим туннелям.

По умолчанию клиентский endpoint доступен на `ENTRY:443/UDP`, а публичный
межсерверный endpoint - на `EXIT:443/UDP` только для IPv4 ENTRY. Локальный
userspace-AWG3 порт ENTRY отделён от клиентского сокета и разрешён только для
публичного IPv4 EXIT. Установщик требует по одному постоянному публичному IPv4
на сервер, добавляет адресные правила и удаляет прежние общие разрешения.
Порт `awg-old` открывается и закрывается одновременно с самим интерфейсом.
Для userspace-интерфейса `awg-mobile` с профилем mobile/AWG3+ прямой UDP/8443
открывается на WAN только пока интерфейс активен. Его закрытый ключ, PSK и
`HeaderProtectionKey` входят в порогово защищённый runtime-пакет. Старое
перенаправление внешнего UDP/53 удаляется автоматически; DNS/53 разрешён только
внутри клиентских интерфейсов.

UFW управляется авторитетно. При первой установке или изменении WAN-интерфейса,
SSH-портов, AWG-портов, адреса второго сервера либо VPN-подсетей прежний набор
правил сбрасывается и создаётся заново после проверки входных параметров. Это
удаляет случайные разрешения, оставленные образом VPS или предыдущей
конфигурацией. При неизменных параметрах повторный deploy не пересобирает UFW.
