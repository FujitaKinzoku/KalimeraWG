# Реализация AWG 3+ в KalimeraWG

KalimeraWG использует два независимых userspace-контура: проверенный AWG 3.0
между ENTRY и EXIT и клиентский mobile/AWG3+ на AWG 3.1. Основной клиентский
интерфейс, совместимый интерфейс `old`, mobile/AWG3+ и межсерверный интерфейс
разделены по бинарникам, ключевому материалу, подсетям и локальным UDP-сокетам.
Перед применением на конкретном хостинге необходимо выполнить описанный ниже
цикл чистой приёмки.

## Совместимость клиентов

- `performance`, `balanced`, `masking`: клиенты, для которых реальным handshake
  подтверждён расширенный ASC (`S1-S4`, диапазоны `H1-H4`, `I1-I5`).
- `mobile` и его явные алиасы `mobile-awg3`, `mobile/awg3+`: отдельный
  userspace-интерфейс `awg-mobile`, подсеть, закрытый ключ и прямой UDP/8443.
  Клиентский конфиг предназначен для AmneziaWG 5.0.1.5 или новее и содержит
  полный поддерживаемый userspace-набор AWG 3.1.
- `old`: отдельный интерфейс `awg-old`, отдельная подсеть, UDP-порт, закрытый ключ
  и peer-хранилище. Конфиг содержит базовый ASC с одиночными `H1-H4` и не
  смешивается с современным интерфейсом.

`awg-old` по умолчанию не запускается. Первый `vpn-user NAME old` включает его
автоматически. Дальнейшее состояние управляется независимо командами
`awg-old status`, `awg-old on` и `awg-old off`; выключение не удаляет клиентов.
Аналогично mobile/AWG3+ управляется командами `awg-mobile status|on|off`. Он
слушает прямой UDP/8443 только во включённом состоянии. Внешний UDP/53 не
перенаправляется и используется исключительно как DNS внутри VPN.

## Клиентский mobile/AWG3+

Сервер и клиент получают согласованный набор полей:

| Группа | Поля |
|---|---|
| junk и padding | `Jc`, `Jmin`, `Jmax`, `S1-S4` |
| заголовки и CPS | `H1-H4`, `I1-I5` |
| защита заголовка | отдельный общий `HeaderProtectionKey` |
| обновление ключей | `RekeyAfterTime`, `RekeyTimeout`, `RejectAfterTime` |
| keepalive | `KeepaliveTimeout`, `MaxHandshakeAttempts`, `PersistentKeepalive` |
| дополнительная маскировка | `ContentPaddingAddition`, `RandomTrailers`, `DisableCookies` |

`DisableCookies` явно задаётся как `off`: cookie-механизм остаётся доступен для
защиты от перегрузки, при этом поле всё равно входит в согласованный профиль.

`S1-S4` всегда не меньше 12, все `I1-I5` заполнены, а
`HeaderProtectionKey` хранится в Ansible Vault и runtime-пакете. Поле
`AdvancedSecurity` намеренно не экспортируется: закреплённый userspace UAPI
AWG 3.1 его не принимает. Это не скрытый режим и не частичный профиль, а
ограничение выбранного upstream userspace backend.

Mobile использует отдельные закреплённые сборки `amneziawg-go` и
`amneziawg-tools` 3.1. Поэтому его обновление и перезапуск не заменяют бинарники
проверенного межсерверного AWG 3.0. Служба получает конфигурацию через systemd
credentials, а открытая runtime-копия остаётся только в `/run`.

Все серверные S/H-параметры копируются в клиентский конфиг без изменения.
Меняются только документированные клиентские junk-параметры и ключевой материал.
Для современных профилей `I1` является 1200-байтным QUIC Initial-подобным
пакетом: длинный заголовок QUIC v1, динамические DCID/SCID, согласованная
varint-длина и случайное заполнение. `I2-I5` имеют форму коротких QUIC-пакетов
разных ограниченных размеров. В пределах каждого интерфейса вся пятёрка
одинакова на сервере и у клиентов ради совместимости реализаций, которые не
принимают разные I-параметры. Динамические `<r>`-поля меняются при каждой
отправке. Каждый `<r N>` не превышает документированный предел 1000 байт;
более длинное случайное заполнение представляется несколькими соседними тегами.
Поскольку поддерживаемые upstream-теги не рассчитывают QUIC AEAD,
сигнатура является структурно QUIC-подобной, но не полноценным сеансом HTTP/3.

## Межсерверный канал

- реализация в пространстве пользователя `amneziawg-go` - `v3.0.20260805`, commit
  `08d68cdae27762c3e07f36bbb12d2bad32f81926`;
- `amneziawg-tools` - `v3.0.20260805`, commit
  `9f70177d204d5be66c5b043518a57b7d62b3f9d1`;
- Go `1.25.12`, официальный архив с закреплённым SHA-256;
- отдельные закрытые ключи и PSK для ENTRY и EXIT;
- общий `HeaderProtectionKey`, причём `S1-S4 >= 12` согласно upstream;
- заполнение содержимого и тайминги AWG 3+ задаются диапазонами;
- интерфейс `awg3` запускается собственной systemd-службой, без подмены
  клиентского kernel-интерфейса `awg0`.
- публичный endpoint межсерверного канала по умолчанию расположен на
  `EXIT:443/UDP`; клиенты используют `ENTRY:443/UDP`;
- локальный userspace-AWG3 на ENTRY использует отдельный управляемый порт, а
  UFW принимает его только от постоянного публичного IPv4 EXIT сервера.

## Автоматический MTU

На каждой стороне бинарным поиском определяется максимальная нефрагментируемая
IPv4-полезная нагрузка ICMP до публичного адреса peer. Временный доступ ICMP
ограничен этим единственным адресом и удаляется обязательным блоком `always`.
Из двух направлений выбирается меньший безопасный MTU межсерверного `awg3` не
выше 1420 с резервом 80 байт, максимальным заполнением содержимого и `S4`.
Современный клиентский MTU равен `min(MTU awg3, 1380)`, поэтому он никогда не
превышает MTU следующего туннеля. Legacy-интерфейс дополнительно ограничен MTU
1280. На время проверки устанавливается `net.ipv4.icmp_echo_ignore_all=0`, а в
обязательном блоке завершения - `net.ipv4.icmp_echo_ignore_all=1`.
Проверка после запуска подтверждает выбранный MTU интерфейса, свежий handshake
и состояние AWG 3+ без повторного включения ответов на ping.

Официальный релиз `amneziawg-go v3.0.20260805` не содержит готового Linux-
бинарника с требуемой реализацией. Поэтому каждый сервер один раз собирает
официальный исходный commit закреплённым Go toolchain, проверяет ревизию и
кэширует бинарник по commit и архитектуре. Повторные установки на том же
сервере сборку не повторяют; рабочие файлы заменяются атомарно.
TCP использует `--clamp-mss-to-pmtu`.

## Приёмка на новом окружении

1. Чистая установка на двух одноразовых Ubuntu 24.04 VPS.
2. Второй deploy должен дать `changed=0` для управляемых настроек.
3. `awg-health --strict` на обоих серверах.
4. Перезагрузка обоих серверов и повторная строгая проверка.
5. Реальный handshake и трафик для KeeneticOS 5.1.3.
6. Реальный handshake и трафик профиля `old` для KeeneticOS 4.3.8.
7. Реальный handshake профиля `mobile/AWG3+` в AmneziaWG 5.0.1.5 или новее.
8. Проверка крупными пакетами и TCP/UDP-трафиком без внешней фрагментации.
