## 🚀 Быстрый старт

Нужны две чистые VPS с Ubuntu 24.04 LTS и публичными IPv4:

- **ENTRY сервер** — принимает VPN-клиентов; обычно размещается в России;
- **EXIT сервер** — выпускает основной иностранный трафик; обычно размещается
  в нужной зарубежной географии.

На ENTRY сервере выполните:

```bash
curl -fsSL https://raw.githubusercontent.com/FujitaKinzoku/KalimeraWG/main/install.sh | bash
```

**Одна команда · обычно 20–40 минут · два чистых Ubuntu 24.04 сервера.**<br>
Результат: работающий каскад ENTRY→EXIT и защищённая конфигурация первого
VPN-клиента.

<details>
<summary><b>Ручная установка через Git</b></summary>

Этот вариант позволяет сначала просмотреть файлы репозитория:

```bash
apt-get -o DPkg::Lock::Timeout=600 update
apt-get -o DPkg::Lock::Timeout=600 install -y git
cd /root
git clone https://github.com/FujitaKinzoku/KalimeraWG.git
cd KalimeraWG
chmod +x deploy
./deploy
```

</details>

Установщик на русском языке запросит адреса серверов, текущие и новые
SSH-порты, начальные пароли, административный публичный SSH-ключ, режим
RU-трафика, DNS и имя первого VPN-пользователя. Значение в квадратных скобках
принимается клавишей Enter.

Вводится только строка публичного ключа `.pub`. Private SSH key вводить нельзя.
Перед закрытием старых SSH-портов установка остановится: сначала проверьте вход
по ключу на оба сервера через новые порты. Fail2Ban включится только после
подтверждения рабочего доступа.

```bash
./deploy --resume   # продолжить прерванную или повторить готовую установку
./deploy --summary  # показать итог без подключения и изменения серверов
./deploy --terminal-only  # обновить только терминал и справку без переподключения SSH
```

<details>
<summary><b>Что именно установщик меняет на серверах</b></summary>

- устанавливает закреплённые компоненты AmneziaWG, userspace-движок AWG 3+ и
  необходимые системные пакеты;
- создаёт независимые клиентский, совместимый и межсерверный VPN-интерфейсы;
- настраивает forwarding, policy routing, `ipset`, `iptables`, NAT и UFW;
- устанавливает dnsmasq, Unbound с DoT и при необходимости sing-box с DoH;
- устанавливает закреплённый `ble.sh`, подсветку команд и Kali-подобное
  приглашение Bash на обоих серверах;
- укрепляет SSH, переводит его на выбранный порт и только после проверки ключа
  включает Fail2Ban;
- устанавливает systemd-службы, watchdog, аудит, обслуживание и автоматические
  обновления безопасности;
- хранит резервные копии только в `/root/config-backups`, а секреты — в
  зашифрованном Ansible Vault вне Git.

Повторный запуск идемпотентен: готовая конфигурация приводится к заданному
состоянию без создания дубликатов правил.

</details>

## ✨ Преимущества KalimeraWG

Первая версия KalimeraWG основана на проверенном снимке, который прошёл
несколько чистых установок и повторных развёртываний. В неё уже входят последние
улучшения эксплуатационной надёжности:

- отдельный userspace-канал AWG 3+ между ENTRY и EXIT с независимыми ключами,
  PSK и параметрами маскировки;
- двустороннее измерение PMTU и автоматическое согласование MTU межсерверного,
  обычного, mobile- и legacy-сегментов;
- проверенный профиль AmneziaWG для iOS на включаемом по требованию
  `UDP/8443`, не занимающий внешний порт без mobile-клиентов;
- отдельный совместимый интерфейс для старых Keenetic, который также включается
  только при появлении соответствующего пользователя;
- безопасное создание, просмотр и отзыв клиентов командами `vpn-user`, включая
  контроль активных peer без вывода ключевого материала;
- защита обновлений ядра: перед перезагрузкой проверяются заголовки и DKMS-модуль
  AmneziaWG для текущего и следующего ядра;
- ранняя проверка системного DNS и повторные попытки APT защищают чистую
  установку от кратковременных отказов DNS и зеркал провайдера;
- проверяемая сводка подключений, DNS, MTU и firewall при входе, строгий аудит и
  Telegram-уведомления о перезагрузках, отказах и восстановлении;
- идемпотентное повторное развёртывание с обязательным восстановлением временных
  правил APT, UFW и ICMP после успеха или ошибки.

<a id="benefits"></a>

## 💡 Что даёт такой каскад

Это не просто два VPN подряд, а управляемая система маршрутизации:

- российские ресурсы могут видеть IP ENTRY сервера либо российского
  SOCKS5/SOAX-прокси;
- иностранные ресурсы видят IP EXIT сервера;
- расширенные клиенты работают через `awg0`, мобильный QUIC-подобный профиль —
  через `awg-mobile`, а KeeneticOS 4.3.x — через `awg-old`;
- между ENTRY и EXIT работает отдельный туннель AmneziaWG 3+ `awg3` в пространстве пользователя;
- для межсерверного канала используются доступные в закреплённой реализации
  AWG 3+ механизмы `HeaderProtectionKey`, `ContentPaddingAddition`, диапазоны
  таймингов, `I1–I5` и динамический `PersistentKeepalive`;
- двусторонний PMTU измеряется автоматически, после чего согласованные MTU
  применяются к межсерверному и клиентскому сегментам каскада;
- DNS-запросы клиентов принудительно направляются на управляемый резолвер;
- конкретный домен можно отправить через ENTRY, EXIT или RU-маршрут;
- конкретные TCP-порты RU-направления можно пустить напрямую через ENTRY,
  минуя ограниченный прокси.

Шифрование описывается точно по сегментам: AWG защищает клиентский туннель до
ENTRY и межсерверный туннель ENTRY→EXIT; DoT/DoH шифруют DNS-транспорт; HTTPS
дополнительно защищает соединение от точки выхода до сайта. Проект не заявляет,
что произвольный незашифрованный протокол становится end-to-end зашифрованным
после выхода из VPN.

<a id="routing"></a>

## 🔀 Схема маршрутизации

```text
VPN-клиент
    │
    │ AmneziaWG awg0
    ▼
ENTRY сервер (обычно RU)
    ├── RU-трафик ──────────────► ENTRY WAN или SOCKS5/SOAX
    │
    └── основной/иностранный ───► AmneziaWG 3+ awg3 ─► EXIT ─► Интернет
```

| Политика | Маршрут |
|---|---|
| обычный трафик и `se-domain` | через EXIT сервер |
| `entry-domain` | напрямую через WAN ENTRY сервера |
| RU-сети и `ru-domain` | через ENTRY или SOCKS5/SOAX |
| `force_exit` / `force_ru` | принудительный выбор маршрута |

Разделение выполняют `ipset`, `iptables`, метки пакетов и маршрутизация по политикам:
метка `0x1` использует таблицу `100` для EXIT; метка `0x2` использует таблицу `200`
для RU-прокси. Пользовательские доменные списки после чистой установки пусты.

### Точечное управление доменами

```bash
ru-domain add example.ru       # RU-маршрут
se-domain add example.com      # через EXIT сервер
entry-domain add example.org   # напрямую через ENTRY сервер
```

Команды поддерживают `list`, `add`, `del` и `clear`. После изменения политика
DNS и маршрутизации применяется атомарно. Динамические `force_ru`, `force_exit`
и `force_entry_bank` очищаются совместно, поэтому перенос домена между списками
не оставляет старого маршрута; адреса снова добавляются dnsmasq при следующем
DNS-запросе клиента.

### Порты в обход RU-прокси

Не каждый SOCKS5-провайдер поддерживает все протоколы и порты. Например, может
понадобиться прямой маршрут через ENTRY для SSH, IMAP или SMTP. Управление
выполняет `ru-direct-ports`; чистая установка не добавляет порты автоматически.

```bash
ru-direct-ports list
ru-direct-ports add 22
ru-direct-ports add 993
ru-direct-ports del 22
ru-direct-ports clear
ru-direct-ports apply
```

Перед добавлением убедитесь, что выбранный порт действительно должен обходить
прокси: правило действует только на TCP-трафик соответствующих RU-направлений.
Порты хранятся в отдельном `ipset bitmap:port`, поэтому ограничения
`iptables multiport` на 15 значений нет, а сама цепочка остаётся короткой при
любом разумном количестве портов. Порт TCP/25 намеренно запрещено добавлять.

### Готовый профиль доменов и прямых портов

Дополнительный профиль с RU-сервисами проверки IP, прямым маршрутом Sberbank
через ENTRY и распространёнными TCP-портами можно применить после установки:

```bash
cd /root/KalimeraWG
scripts/apply-policy-profile.sh
```

Обычный запуск только добавляет отсутствующие значения и сохраняет остальные
пользовательские правила. Для точной замены всех трёх доменных списков и списка
прямых RU-портов используйте осознанно:

```bash
scripts/apply-policy-profile.sh --replace
```

Скрипт пакетно подготавливает изменения, а затем по одному разу применяет DNS и
маршрутизацию. Если применение завершается ошибкой, предыдущие списки
восстанавливаются автоматически. Такой порядок исключает серию быстрых
перезапусков `dnsmasq` и блокировку службы ограничителем частоты запусков
systemd. В конце выполняется строгая проверка `awg-health`.

<a id="dns"></a>

## 🌐 DNS с учётом маршрута

Клиенты отправляют DNS только на ENTRY сервер:

```text
клиент → dnsmasq → доменная политика
                    ├─ основной DNS → Unbound → DNS-over-TLS
                    └─ RU при прокси → sing-box → DoH через SOCKS5
```

- основной резолвер — Unbound с DoT; по умолчанию Mullvad;
- при активном RU-прокси RU split DNS использует Yandex DoH через тот же
  SOCKS5-маршрут;
- при прямом RU-режиме sing-box отключён, RU-запросы используют основной DoT;
- DNS enforcement перехватывает клиентские UDP/TCP-запросы на порт 53 и не
  позволяет обойти управляемый resolver обычным внешним DNS;
- DoT/DoH endpoints, TLS names и DoH path можно задать в установщике либо
  безопасно изменить после установки. Локальные изменения переживают
  `deploy --resume`, проверяются реальным DNS-запросом и откатываются при сбое.

```bash
dns-status                              # вся активная DNS-схема и проверки
dot-switch status                       # текущий основной DoT
dot-switch mullvad                      # вернуть Mullvad
dot-switch custom 1.1.1.1 cloudflare-dns.com
doh-switch status                       # текущий RU DoH
doh-switch yandex                       # вернуть Yandex
doh-switch custom 1.1.1.1 cloudflare-dns.com /dns-query
```

`doh-switch` доступен, если при установке был настроен RU-прокси. Команда
`reset` у `dot-switch` и `doh-switch` удаляет локальное переопределение и
возвращает значения из зашифрованного inventory.

Так DNS для проксируемых RU-доменов запрашивается через RU-прокси и лучше
соответствует выбранной географии. Для остальных доменов используется основной
DoT-путь. Абсолютное совпадение геолокации ответа не гарантируется: оно также
зависит от authoritative DNS, CDN и выбранного DNS-провайдера.

<a id="proxy"></a>

## 🇷🇺 Зачем нужен SOAX или другой SOCKS5

SOAX полезен, если российский ресурс должен видеть residential/mobile RU IP,
если IP хостинга ENTRY блокируется либо если ENTRY физически находится не в
нужном регионе. Архитектура поддерживает и другой SOCKS5.

Если прокси не нужен, выбирается прямой режим: RU-трафик выходит через ENTRY,
а sing-box и watchdog отключаются. При активном прокси watchdog работает в
режиме fail-open: после устойчивого отказа RU-трафик переключается на ENTRY WAN,
чтобы клиенты не остались без связи, а после восстановления возвращается к
прокси.

При установке и после `ru-proxy-set` ENTRY автоматически выполняет SOCKS5
`UDP ASSOCIATE` и реальный DNS-запрос через UDP relay. Если UDP не поддерживается,
TCP и RU DoH продолжают идти через прокси, а RU UDP безопасно направляется
напрямую через ENTRY. Результат хранится в маршрутизирующей политике и
контролируется `awg-health`.

`ru-proxy-set` сохраняет локальное переопределение в защищённом файле
`/etc/awg/ru-proxy-override.json` с правами `0600`, перезапускает sing-box,
дожидается `sb-ru`, повторно создаёт таблицу `200` и проверяет маршрут. Следующий
deploy учитывает это переопределение. Файл остаётся только на ENTRY и никогда не
попадает в Git.

<a id="clients"></a>

## 👤 Гибкая генерация клиентских конфигураций

Система поддерживает **динамическую генерацию** конфигураций под разные
потребности. Каждый пользователь получает собственные `Jc/Jmin/Jmax`, private
key, PSK и IP-адрес. Современный профиль использует полный набор полей,
поддерживаемый выбранной реализацией и совместимым клиентом: `S1–S4`, диапазоны
`H1–H4`, `I1–I5`, согласованный MTU и динамические junk-параметры.

<details>
<summary><b>Технические подробности S1–S4, H1–H4 и I1–I5</b></summary>

Параметры `S1–S4`, динамические диапазоны `H1–H4` и `I1–I5` в современной клиентской
конфигурации **точно совпадают** с интерфейсом `awg0` ENTRY сервера. AmneziaWG
требует одинаковые интерфейсные параметры на обеих сторонах; различаться могут
только `Jc/Jmin/Jmax`. Это позволяет всем пользователям работать через один
интерфейс и один UDP-порт без потери динамических заголовков. Требование
зафиксировано в [официальной документации AmneziaWG](https://github.com/amnezia-vpn/amneziawg-linux-kernel-module#configuration).

На стандартном UDP/443 `I1` формируется как QUIC Initial-подобный пакет ровно
1200 байт: длинный заголовок QUIC v1, случайные `DCID/SCID`, корректная
QUIC-varint длина, случайный packet number и заполнение. Размеры идентификаторов
и длина packet number выбираются индивидуально при установке, а содержимое
динамических полей меняется при каждой отправке. `I2–I5` имеют форму коротких
QUIC-заголовков разных ограниченных размеров. Каждый динамический тег `<r N>`
ограничен документированными 1000 байтами; если случайная часть длиннее, она
разбивается на несколько последовательных тегов без изменения итогового пакета.

Upstream-теги `<b>` и `<r>` не вычисляют AEAD настоящего QUIC-сеанса, поэтому
это честно называется **QUIC-подобной сигнатурой**, а не полноценным HTTP/3.
Она улучшает форму первого UDP-трафика, но не гарантирует обход любого DPI.
Размер `I1` не превышает минимальный размер IPv6 MTU с учётом внешних
заголовков и проверяется тестами. Это маскировка перед handshake, а не замена
шифрования AWG.

```text
I1 = <b 0xc30000000108><r 8><b 0x08><r 8><b 0x004496><r 1000><r 174>
I2 = <b 0x40><r 127>
I3 = <b 0x41><r 95>
I4 = <b 0x42><r 63>
I5 = <b 0x43><r 31>
```

Все пять значений копируются в современный клиент без изменения. Это также
обходит известную несовместимость некоторых клиентов, при которой активный
`I1` только на одной стороне препятствует handshake. Профиль `old` намеренно
не получает `I1–I5`, поскольку старые реализации Keenetic их не поддерживают.

Пример динамических диапазонов общего интерфейса:

```text
H1 = 112345678-112789012
H2 = 623456789-623987654
H3 = 1123456789-1123987654
H4 = 1678901234-1679567890
```

</details>

### Профили клиентов

Основные профили `performance`, `balanced` и `masking` соблюдают опубликованные
границы AWG 2.0: `S1–S3` находятся в
пределах `0–64`, `S4` — `0–32`, `Jc` — не выше `10`, а `Jmin/Jmax` — в
пределах `64–1024`. Фактически используются ненулевые безопасные поддиапазоны:
`S1/S2 = 16–64`, `S3 = 16–64`, `S4 = 12–32`. Для AWG 3+ это также выполняет
требование `S1–S4 >= 12`, необходимое для `HeaderProtectionKey`.
Отдельный профиль `mobile` намеренно повторяет параметры реально работающего
конфига официального AmneziaWG для iOS (`S1=134`, `S2=79`, `S3=17`, `S4=0`),
а не смешивает их с основным интерфейсом.

| Профиль | Jc | Диапазон Jmin | Диапазон Jmax | Назначение |
|---|---:|---:|---:|---|
| **performance** | 4 | 64 | 80–96 | Максимальная скорость, документированный минимум junk-пакетов |
| **balanced** | 5–7 | 64–96 | 128–384 | Сбалансированный режим |
| **masking** | 8–10 | 96–192 | 384–1024 | Усиленная маскировка без превышения MTU |
| **mobile** | 5 | 10 | 50 | Проверенный iOS-профиль, QUIC Initial-подобный `I1`, прямой UDP/8443 |
| **old** | 4–6 | 64 | 80–96 | KeeneticOS 4.3.x, базовый ASC на отдельном интерфейсе |

Даже профиль максимальной производительности использует динамические
заголовки. Разница в скорости определяется прежде всего количеством и размером
junk-пакетов.

### Использование

```bash
# С явным указанием профиля
vpn-user fast-client performance
vpn-user normal-client balanced
vpn-user protected-client masking
vpn-user iphone mobile
vpn-user old-router old

# Интерактивный выбор профиля
vpn-user client-name

# Просмотр и отзыв локально созданных пользователей
vpn-user list
vpn-user delete client-name

# Управление отдельным интерфейсом старых клиентов
awg-old status
awg-old on
awg-old off

# Управление отдельным мобильным интерфейсом
awg-mobile status
awg-mobile on
awg-mobile off
```

`vpn-user list` показывает профиль, адрес, источник и возраст последнего
рукопожатия без вывода ключей. Удаление немедленно отзывает peer, удаляет
рабочую клиентскую конфигурацию и сохраняет защищённую резервную копию в
`/root/config-backups/entry/clients/deleted`. Пользователи из зашифрованного
inventory намеренно не удаляются локальной командой: иначе следующий deploy
восстановил бы их. Таких пользователей нужно удалить на управляющем компьютере
и применить `./deploy --resume`.

Если production inventory был создан до появления отдельного mobile-интерфейса,
его можно безопасно добавить без переустановки серверов:

```bash
./deploy --resume --enable-mobile
vpn-user iphone mobile
```

Установщик создаёт новый закрытый ключ непосредственно в зашифрованном Vault,
выбирает непересекающуюся подсеть, добавляет профиль UDP/8443 и оставляет службу
выключенной. Первый `vpn-user NAME mobile` включает её только после создания
пира. Повторный `--enable-mobile` идемпотентен и не ротирует созданный ключ.

Каждый новый клиент получает адрес с маской своей VPN-подсети, например
`Address = 10.66.0.2/24`, а не хостовой маской `/32`. Поэтому Keenetic создаёт
связанный маршрут `10.66.0.0/24` через AWG-интерфейс и достигает внутреннего DNS
`10.66.0.1` без отдельной статической политики. Клиентский `AllowedIPs` содержит
только общие маршруты `0.0.0.0/0, ::/0`: отдельный DNS-маршрут там больше не
нужен. DHCP роутера может раздавать `10.66.0.1` всем устройствам без внешних
DNS-настроек на каждом клиенте. Для `mobile` и `old` автоматически применяются
маска и DNS их собственной подсети. На сервере адрес каждого peer по-прежнему
ограничен обязательным индивидуальным `/32` для cryptokey routing.

Расширенные профили содержат `S1–S4`, диапазоны `H1–H4` и `I1–I5`, однако их
совместимость должна подтверждаться конкретным клиентом. Профиль `mobile`
использует отдельные подсеть, ключ и интерфейс, внешний endpoint `UDP/8443` и
подтверждённую AmneziaWG для iOS QUIC Initial-подобную подпись `I1`. `I2–I5` в нём
намеренно отсутствуют: их заполнение вызывало отказ handshake в мобильном
клиенте. Профиль `old` формируется для отдельного
UDP-порта, подсети, ключа и интерфейса `awg-old`; он использует только
`Jc/Jmin/Jmax`, `S1/S2` и одиночные значения `H1–H4`. Поэтому старое устройство
не заставляет ослаблять параметры остальных клиентов.

Интерфейс `awg-old` не запускается при обычной установке с современным первым
клиентом. Команда `vpn-user NAME old` создаёт первый совместимый конфиг и
автоматически включает интерфейс. `awg-old off` останавливает и отключает его,
не удаляя пользователей; `awg-old on` включает его снова.

`awg-mobile` также не занимает внешний порт постоянно без mobile-клиентов.
Первый `vpn-user NAME mobile` включает интерфейс и прямое правило WAN для
`UDP/8443`. Перенаправления внешнего UDP/53 больше нет: порт 53 остаётся только
внутренним DNS-портом клиентских интерфейсов. При обновлении прежние правила
`UDP/53 → UDP/39746` удаляются автоматически.

QUIC Initial-подобный `I1` является стандартным для новых mobile-конфигов и не
ротируется при повторном `--resume`. Для явного применения к прежней установке:

```bash
./deploy --resume --mobile-i1-mode quic-ios
vpn-user iphone mobile
```

Для совместимости сохранён обратный переход на DNS-подобную подпись:
`./deploy --resume --mobile-i1-mode dns-ios`. После любой смены `I1` необходимо
создать новый mobile-конфиг: клиенты одного интерфейса должны использовать
точно те же параметры, что и сервер.

> **Важно:** точное поведение импорта зависит от модели и версии KeeneticOS.
> Каждый тип клиента необходимо подтвердить реальным рукопожатием. Для старых
> реализаций предусмотрен отдельный профиль и интерфейс `old`.

<a id="awg3"></a>

## 🔐 Межсерверный канал AWG 3+

ENTRY и EXIT соединяются отдельным интерфейсом `awg3`. По умолчанию клиенты
подключаются к `ENTRY:443/UDP`, а ENTRY устанавливает межсерверное соединение с
`EXIT:443/UDP`. На ENTRY userspace-AWG3 получает отдельный автоматически
выбранный локальный порт, поскольку независимые `awg0` и `awg3` не должны
конкурировать за один сокет UDP/443. UFW принимает этот локальный порт только
от известного публичного адреса EXIT. Канал не делит ключи или настройки с
клиентским `awg0`; установщик проверяет handshake и подбирает безопасный MTU.

<details>
<summary><b>Реализация HeaderProtectionKey, ContentPaddingAddition и автоматического PMTU</b></summary>

ENTRY↔EXIT использует закреплённые версии исходных проектов `amneziawg-go
v3.0.20260805` и `amneziawg-tools v3.0.20260805`. Официальный выпуск
`amneziawg-go` не публикует подходящий готовый Linux-бинарник, поэтому роль
собирает неизменяемые upstream-коммиты официальным закреплённым Go toolchain.
Полученные бинарники кэшируются по commit и архитектуре: повторный deploy их не
пересобирает, а установка в рабочий путь выполняется атомарно. Это та же полная
upstream-реализация AWG 3+, без отключения возможностей. Помимо ASC-параметров канал
включает общий `HeaderProtectionKey`, `ContentPaddingAddition`, диапазоны
таймингов и случайный диапазон `PersistentKeepalive`. Ключ защиты заголовка,
закрытые ключи и PSK хранятся только в Ansible Vault.

Перед запуском канала оба сервера независимо измеряют IPv4 PMTU друг до друга
без фрагментации (`ping -M do`). На время измерения создаётся только временное
ICMP-правило от постоянного публичного IPv4 второго сервера; блок `always`
удаляет правило и при успехе, и при ошибке. Общим MTU становится меньший
результат двух направлений с резервом на userspace AWG, `S4` и максимальное
заполнение содержимого. Межсерверный `awg3` получает максимально безопасное
значение не выше 1420. Современный `awg0` и создаваемые конфиги получают
`min(MTU awg3, 1380)`, поэтому клиентский пакет всегда помещается в следующий
туннель без лишнего уменьшения пропускной способности AWG3. Legacy-интерфейс
дополнительно ограничен 1280 ради совместимости. Если
измерение невозможно, используется консервативное резервное значение; TCP MSS
автоматически зажимается по фактическому PMTU. Путь от конкретного клиента до
ENTRY заранее неизвестен, поэтому при необычно малом MTU его доступа может
потребоваться отдельное уменьшение. На время измерения ответы ICMP echo
включаются, после чего принудительно устанавливается
`net.ipv4.icmp_echo_ignore_all = 1` на обоих серверах.

</details>

Первый клиент создаётся автоматически в конце установки:

```text
/root/.local/share/awg-iac/production/clients/ИМЯ.conf
```

Файл имеет права `0600`. Его содержимое не печатается: внутри находятся private
key и PSK. Передавайте конфигурацию только по доверенному каналу.

<a id="telegram"></a>

## 📡 Мониторинг через Telegram

При установке можно включить **мониторинг через Telegram**. Токен бота и идентификатор чата
запрашиваются без отображения и сохраняются в зашифрованном Ansible Vault.
KalimeraWG не использует общего проектного бота: каждый оператор подключает
собственного бота и собственный чат, а при ненужном мониторинге полностью
отключает эту возможность. Если бота ещё нет, установщик показывает краткие
шаги создания через официальный проверенный `@BotFather` и команду `/newbot`.
Полная строка BotFather вида `1234567890:AA...` является одним токеном и
вводится целиком вместе с двоеточием. Chat ID указывается отдельно числом;
идентификатор группы обычно начинается с `-100`.
Если Chat ID ещё неизвестен, поле можно оставить пустым: установщик проверит
токен, попросит отправить боту сообщение и автоматически возьмёт ID последнего
доступного чата через официальный Telegram Bot API. При повторных установках
можно вводить сохранённый Chat ID — для одного пользователя или группы он не
зависит от VPS и остаётся прежним.

Ни токен, ни Chat ID не передаются проекту KalimeraWG и не записываются в Git.
Они используются только установленными узлами и хранятся в Ansible Vault.
Во время установки Telegram-таймер остаётся остановленным. Он включается
только после успешной строгой проверки ENTRY и EXIT, поэтому промежуточные
состояния деплоя не создают ложных тревог.

Системный таймер регулярно запускает безопасный аудит, который проверяет:

- состояние AWG-туннелей и строгий `awg-health`;
- отсутствие неисправных модулей systemd;
- свободное место на корневой файловой системе;
- активность UFW и Fail2Ban.

Telegram получает отдельные уведомления:

- о перезагрузке ENTRY или EXIT и состоянии узла после запуска;
- о длительной потере handshake между ENTRY и EXIT;
- о переходе проверки сервера в аварийное состояние и восстановлении;
- об автоматическом fail-open RU-прокси и возврате штатной прокси-маршрутизации.

Ручное `ru-proxy off` считается намеренным действием и тревогу не создаёт.
Повторяющиеся сообщения при неизменном состоянии не отправляются. Доставку
можно безопасно проверить без отключения служб командой `telegram-test`.
Мониторинг настраивается один раз во время установки и далее работает
автоматически через systemd timer.

<a id="terminal"></a>

## 💻 Терминал в стиле Kali

На ENTRY и EXIT устанавливается единое интерактивное окружение Bash:

- двухстрочное приглашение в стиле Kali с меткой роли `ENTRY` или `EXIT`;
- подсветка существующих команд, встроенных функций, путей и синтаксических
  ошибок через `ble.sh`;
- автоматические предложения, улучшенное дополнение и редактирование истории;
- цветной вывод `ls`, `grep`, `ip`, `diff`, systemd и читаемый `less`;
- короткое русское объяснение ненулевого кода завершения команды.
- цветная сгруппированная справка по управлению KalimeraWG при каждом новом
  SSH-входе или терминальном сеансе;
- цветная сводка фактических подключений, маршрута RU-трафика, активных
  DoT/DoH, согласованного MTU и защиты. Она выполняет безопасный `server-audit`,
  не выводит секреты и доступна отдельно командой `kalimera-status`.

Повторный полный показ — `kalimera-help`; только текущая сводка —
`kalimera-status`.

Настройка применяется только к интерактивному Bash. В CI, перенаправленном
выводе, `TERM=dumb` или при установленной переменной `NO_COLOR` цвет отключается
автоматически. Исходный `/etc/bash.bashrc` перед первым изменением сохраняется в
`/root/config-backups/terminal`; существующие пользовательские `.bashrc` и
`.blerc` целиком не заменяются: в root `.bashrc` добавляется только отмеченный
управляемый блок в самом конце.

Установщик использует ту же палитру для разделения этапов. После завершения он
показывает отдельными панелями адреса SSH и VPN, схему маршрутизации, DNS,
согласованный MTU, правила внешнего доступа, пути к готовым файлам, команды и
следующие шаги — без вывода закрытых ключей, PSK или паролей.

Подробнее: [оформление терминала и отключение BLE](docs/terminal.md).

<a id="security"></a>

## 🔒 Защита на высоком уровне

Система изначально проектировалась с упором на безопасное развёртывание и
эксплуатацию.

### Защита SSH от перебора

- Fail2Ban включается только в финале установки — после успешной проверки входа
  по административному ключу через новый SSH-порт;
- повторные неудачные попытки входа блокируются, а срок блокировки постепенно
  увеличивается;
- команда `f2b-reset` без аргументов только проверяет jail `sshd`; снятие
  блокировки требует явного IP, а массовое снятие — явного `--all`.

### Строгая конфигурация SSH

- используется аутентификация по публичному ключу, вход по паролю и пустые
  пароли отключаются;
- интерактивная клавиатурная аутентификация, перенаправление X11, SSH-агента и
  TCP отключены;
- число попыток входа и время ожидания авторизации ограничены;
- при смене порта сначала открывается и проверяется новый прослушиватель. Старый порт
  удаляется из конфигурации и UFW только после подтверждённого рабочего входа.

### Шифрование VPN-трафика

- клиентский трафик до ENTRY сервера защищён отдельным туннелем AmneziaWG;
- канал ENTRY↔EXIT также является отдельным шифрованным AmneziaWG-туннелем со
  своими ключами и PSK;
- ключи клиентского и межсерверного туннелей не переиспользуются. После выхода
  трафика из выбранного сервера его сквозное шифрование зависит от протокола
  приложения — например, от HTTPS/TLS.

### Защищённый DNS

- запросы клиентов на UDP/TCP-порт 53 принудительно перенаправляются на
  управляемый DNS ENTRY сервера;
- основной резолвер Unbound обращается к вышестоящему серверу по DNS-over-TLS с проверкой
  TLS-имени. По умолчанию используется Mullvad, но серверы настраиваются;
- при включённом RU-прокси разделённый DNS для RU-доменов работает через
  DNS-over-HTTPS и тот же SOCKS5-маршрут. По умолчанию используется Yandex DoH;
- DoT и DoH шифруют DNS-транспорт до выбранного провайдера, но не скрывают от
  конечных сайтов сам факт соединения и не заменяют HTTPS.

### Секреты и резервные копии

- серверные ключи каскада, его PSK, пароли, учётные данные прокси и токен
  Telegram записываются в зашифрованный Ansible Vault; пароль Vault хранится
  вне Git с правами `0600`;
- Python-зависимости управляющего окружения закреплены вместе с транзитивными
  версиями и SHA256; установка с несовпадающим архивом прекращается;
- CI дополнительно проверяет текущее содержимое и историю Gitleaks, а Dependabot
  предлагает обновления Python-зависимостей и GitHub Actions отдельными PR;
- клиенты, добавленные после установки командой `vpn-user`, неизбежно получают
  собственный private key и PSK в root-only файлах ENTRY; эти файлы имеют права
  `0600`, находятся вне Git и никогда не выводятся командой установки;
- готовая конфигурация первого клиента сохраняется только локально в каталоге
  `clients` с ограниченными правами и не выводится целиком в журнал установки;
- конфигурационные резервные копии разрешены только в `/root/config-backups`.

### Обновления и контроль состояния

- обновления безопасности Ubuntu устанавливаются автоматически;
- перед завершением обновления KalimeraWG устанавливает заголовки и проверяет
  DKMS-модуль AmneziaWG как для работающего, так и для следующего загрузочного
  ядра, поэтому плановая перезагрузка не оставляет каскад без модуля;
- при запрете IPv6 установщик сохраняет исходные конфигурации `ifupdown` в
  `/root/config-backups/security/network` и комментирует только несовместимые
  IPv6-hooks; IPv4-адрес, шлюз, DNS и активный сетевой менеджер не изменяются;
- ожидание `systemd-networkd-wait-online` отключается только для WAN,
  который явно имеет состояние `unmanaged`; это предотвращает ложный отказ
  аудита на VPS с `ifupdown`, не останавливая работающую сеть;
- плановое обслуживание выполняется systemd-таймерами и командами
  `maintenance` и `update-all`;
- `update-all` обновляет Ubuntu и заранее собирает DKMS для следующего ядра, но
  намеренно не меняет AmneziaWG, sing-box и AWG3 внутри работающего каскада;
- явная команда `./deploy --resume --update-components` сначала загружает и
  сохраняет предыдущие пакеты на обоих серверах, выбирает единый набор версий,
  применяет проверенный manifest текущего выпуска KalimeraWG, проверяет весь
  каскад и автоматически возвращает прежние пакеты и inventory при любой ошибке;
- `awg-health --strict` проверяет туннели, маршрутизацию, firewall, DNS и службы,
  а `server-audit` выполняет регулярный аудит без вывода секретов;
- на внешних интерфейсах UFW открывает только фактически используемые TCP-порты
  SSH и UDP-порты AWG; DNS доступен исключительно внутри VPN-интерфейсов;
- клиенты и публичный endpoint межсерверного AWG используют UDP/443 на разных
  серверах; локальный AWG3-порт ENTRY и порт совместимых клиентов разделены;
- межсерверный UDP-порт на ENTRY принимает пакеты только от публичного IPv4
  EXIT, а на EXIT — только от публичного IPv4 ENTRY; широкие прежние правила
  автоматически удаляются;
- входящая и транзитная политики UFW по умолчанию запрещающие; исходящие
  соединения разрешены для DNS, обновлений, прокси и установления туннелей;
  NAT на EXIT применяется только к адресу межсерверного туннеля.

Политика UFW авторитетна: при первой установке или изменении сетевых параметров
старые правила пересобираются. Поэтому дополнительные пользовательские
разрешения UFW следует оформлять как отдельную поддерживаемую настройку проекта,
а не добавлять вручную на сервере.

WAN-интерфейсы определяются автоматически по маршруту IPv4 по умолчанию. Поддерживается
Ubuntu 24.04 LTS, включая 24.04.4 и последующие обновления этой LTS-ветки.

### Безопасное обновление компонентов каскада

Сначала обновите саму копию KalimeraWG обычным проверенным способом и выполните
проверку доступных пакетов:

```bash
maintenance
```

Обычные обновления ОС и ядра устанавливаются отдельно:

```bash
update-all
```

AmneziaWG, sing-box и AWG3 обновляются только с управляющей машины:

```bash
cd /root/KalimeraWG
./deploy --resume --update-components
```

AmneziaWG выбирается единым набором из подключённого официального PPA для ENTRY
и EXIT. До установки текущие и новые `.deb` полностью загружаются локально.
sing-box и исходники AWG3 берутся только из закреплённого manifest текущего
выпуска KalimeraWG с контрольными суммами. После изменения выполняются DKMS,
handshake, DNS, маршрутизация и строгий аудит; неуспешная транзакция откатывается.
Автоматические фоновые обновления этих компонентов намеренно запрещены, чтобы
новая upstream-версия не остановила удалённый каскад без возможности проверки.

<a id="responsible-use"></a>

## ⚖️ Ответственное использование

KalimeraWG предназначен только для законного администрирования собственных
серверов и сетей либо инфраструктуры, на управление которой оператор получил
явное разрешение. Проект не предназначен для несанкционированного доступа,
вмешательства в чужие системы, распространения вредоносного ПО, фишинга,
спама, атак на доступность или использования GitHub как прокси и рабочей
сетевой инфраструктуры. Оператор самостоятельно отвечает за соблюдение
применимого законодательства, правил провайдера и условий используемых
сторонних сервисов.
